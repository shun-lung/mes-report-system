# Bug 紀錄（第 5 階段）

## Bug 報告怎麼寫

好的 Bug 報告讓別人**不用問你就能重現問題**。必填：

| 欄位 | 寫什麼 |
|---|---|
| 編號／標題 | 一句話說出問題 |
| 嚴重度 | 嚴重＝算錯帳、資料損壞；高＝主要功能不能用；中＝有替代做法；低＝顯示或文字 |
| 對應需求／案例 | REQ-xx、TC-xx |
| 重現步驟 | 一步一步，照做就會發生 |
| 預期結果 | 依需求應該怎樣 |
| 實際結果 | 實際發生什麼 |
| 狀態 | 新發現 → 待決定 → 修正中 → 已修正（重測通過）→ 結案；或「不修」並寫原因 |

## BUG-001 已開立、還沒開始生產的製令可以「結案」

| 欄位 | 內容 |
|---|---|
| 嚴重度 | 低 |
| 對應 | REQ-CLOSE-01、TC-34 |
| 重現步驟 | 1. 建立製令並開立（不報工）<br>2. 呼叫 `POST /work-orders/:id/close` |
| 預期結果 | 擋下：還沒開始生產的製令應該用「取消」，不是「結案」 |
| 實際結果 | 結案成功，製令變成 CLOSED |
| 影響 | 網頁上的「結案」按鈕只在生產中、已完工時出現，所以**一般操作碰不到**；只有直接呼叫 API 才會發生。結案後流程卡沒有作廢、訂單明細不能重新轉製令，跟「取消」的效果不同 |
| 原因 | `CloseWorkOrder`（`backend/internal/production/lifecycle.go`）允許的狀態包含 RELEASED |
| 狀態 | **待決定**（請使用者決定要不要修）。測試 TC-34 先標為「已知問題」略過，修好後會自動變成通過 |

## 測試本身的錯誤（不是系統 Bug）

測試失敗不一定是系統錯，也可能是**測試寫錯**。判斷方法：回頭看需求和程式，確認「預期結果」本身對不對。

### TD-001 TC-14～16 第一次執行失敗：上工和報工在同一秒

- 現象：自動下工沒有發生，3 個案例失敗。
- 調查：系統下工的條件是「下工時間必須晚於上工時間」，避免出現 0 分鐘的工時紀錄。測試卻把上工和報工設在同一秒。
- 結論：**測試錯**，系統是對的。真實現場不會在同一秒上工又報完。
- 處理：測試改成上工時間在報工前 1 小時，重跑通過。
