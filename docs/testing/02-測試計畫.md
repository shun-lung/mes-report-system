# 02 測試計畫（第 2 階段）

## 這份文件在做什麼

測試計畫回答「**怎麼測、測到哪裡算完**」。就像旅行前先排行程：去哪裡、帶什麼、哪天回來。
沒有計畫，測試很容易變成「想到什麼測什麼」，測完也說不出到底測了多少。

## 1. 目標

確認報工系統主流程的規則都正確：不會算錯數量、庫存、工時，也不會讓不該發生的操作成功。

## 2. 範圍

| 測 | 不測（下一輪） |
|---|---|
| 製令開立、修改、取消、訂單狀態 | 採購、缺料預警公式 |
| 發料、強制發料 | Excel 匯入 |
| 上工、下工、自動下工 | 角色與權限維護 |
| 報工、不良、重工、到站扣帳 | 拆卡／合併 |
| 撤銷報工 | 看板數字計算、流程卡列印 |
| 完工入庫、結案 | 效能、資安 |

需求清單見 [01-需求追溯表](01-需求追溯表.md)，共 31 條。

## 3. 測試種類

| 種類 | 白話解釋 | 本輪做法 |
|---|---|---|
| 單元測試 | 只測一個小函式，不連資料庫 | 已有生產日計算（`org/workdate_test.go`），本輪不新增 |
| **整合測試** | 連真的資料庫，測一整段業務流程 | **本輪主力**：Go 測試直接呼叫系統的服務程式 |
| 端對端測試（E2E） | 模擬人開瀏覽器點畫面 | 本輪不做自動化，改手動 |
| 手動測試 | 人照步驟在網頁上操作、比對結果 | 畫面相關的 4 個案例 |
| 回歸測試 | 改程式後把舊測試全部重跑，確認沒弄壞別的 | 每次 push 由 GitHub 自動執行 |

為什麼主力選整合測試：報工系統的規則幾乎都在「資料庫交易」裡（扣庫存、改狀態、下工），只有連真的資料庫才測得出來。

## 4. 測試環境

| 項目 | 內容 |
|---|---|
| 資料庫 | 本機 Docker PostgreSQL 裡另開 `mes_test`，與開發用的 `mes` 分開；雲端資料庫完全不碰 |
| 測試資料 | 每個測試開始前清空 `mes_test`，重建一套最小工廠（2 站、3 線、1 個成品、2 種料），測試之間互不影響 |
| 時間 | 固定在 2026-11-10 早班 10:00，不管哪天執行結果都一樣 |
| 工具 | Go 內建 `go test`、GitHub Actions |

詳細操作見 [04-測試環境](04-測試環境.md)。

## 5. 進入與退出條件

**進入條件**（可以開始測）：程式編譯得過、`mes_test` 連得上。

**退出條件**（可以說測完了）：
- 所有自動化案例都執行過。
- 高優先需求的案例全部通過；如果有失敗，必須記錄成 Bug 並由使用者決定處理方式。
- 需求追溯表每一條都有對應案例。

## 6. 角色

| 角色 | 誰 | 做什麼 |
|---|---|---|
| 測試設計與自動化 | Claude | 寫案例、寫測試程式、執行、寫報告 |
| 需求確認、Bug 決策 | 使用者 | 判斷規則對不對、Bug 要不要修 |
| 手動測試 | 使用者 | 在網頁上執行 4 個手動案例 |

## 7. 風險

- 測試資料是簡化版工廠（2 站），真實工廠有 4 站、12 條線，多站的情況只靠規則推論。
- 時間固定在早班，跨班、跨午夜的情況本輪沒測。
- 畫面只做手動測試，前端的顯示錯誤可能漏掉。
