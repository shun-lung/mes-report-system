# 01 需求追溯表（第 1 階段：需求分析）

## 這份表在做什麼

「需求分析」就是先回答：**我們到底要驗證哪些事？**

做法：把規格（`docs/architecture.md`）裡的規則，一條一條改寫成「可以判斷對錯」的句子，再給每條一個編號。

- ✗ 不好測：「報工要正確」→ 怎樣算正確？沒辦法判斷。
- ✓ 好測：「報工數量不能超過本站可報量，超過要被擋下」→ 報 101 雙看有沒有被擋，對錯很清楚。

這張表叫**需求追溯表**（RTM，Requirements Traceability Matrix）。「追溯」的意思是：
- 從需求往下找：這條需求有沒有測試案例？（避免漏測）
- 從測試往上找：這個測試在驗哪條需求？（避免做白工）

## 欄位說明

| 欄位 | 意思 |
|---|---|
| 編號 | REQ-模組-序號，之後測試案例、Bug 報告都用這個編號互相對照 |
| 需求 | 可以判斷對錯的一句話 |
| 來源 | 出自 architecture.md 第幾點 |
| 優先 | **高**＝錯了會算錯帳、庫存或工時；**中**＝流程卡住但不會算錯；**低**＝顯示或方便性 |
| 測試案例 | 對應的案例編號，見 [03-測試案例](03-測試案例.md) |
| 狀態 | 未測 → ✅ 通過／❌ 失敗；手動案例等使用者在網頁上執行 |

> 寫這張表時發現一件事：架構文件第 14 點寫「生產自動產生的完工入庫不可在此沖銷」，但第 25 點的「完工入庫」（暫存倉轉成品倉）是可以沖銷的。兩者說的是不同的東西（前者是報工自動入庫 FG_IN，後者是倉管入庫 TRANSFER），文件用詞容易混淆。這就是需求分析的價值：**還沒測就先找到規格不清楚的地方**。
